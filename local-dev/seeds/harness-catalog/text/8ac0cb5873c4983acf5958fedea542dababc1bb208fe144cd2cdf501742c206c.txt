# KaliBench: A Fine-Grained Benchmark for Cybersecurity Tool Use on Kali Linux with Runtime-Free Verifiable Rewards

[View original diagram](https://arxiv.org/html/2610.02206v1#p1.pic1) ![Refer to caption](https://arxiv.org/html/2610.02206v1/teaser-ori-modified.png)

Figure 1: Why KaliBench Matters? KaliBench enables fine-grained, verifiable evaluation and runtime-free reward training for translating analyst intent into executable Kali commands.

## 1 Introduction

Large language models (LLMs) are increasingly adopted in cybersecurity workflows, ranging from interactive assistants to autonomous agents \[[40](https://arxiv.org/html/2610.02206v1#bib.bib19)\]. Early benchmarks in this domain primarily focus on *knowledge-based* assessment, testing models’ understanding of cybersecurity concepts via multiple-choice \[[36](https://arxiv.org/html/2610.02206v1#bib.bib16), [19](https://arxiv.org/html/2610.02206v1#bib.bib10)\] or structured-answer questions \[[14](https://arxiv.org/html/2610.02206v1#bib.bib6), [3](https://arxiv.org/html/2610.02206v1#bib.bib2)\]. More recent benchmarks move toward *end-to-end agentic* evaluation, measuring model performance in complex environments such as autonomously solving CTF-style challenges \[[32](https://arxiv.org/html/2610.02206v1#bib.bib15), [45](https://arxiv.org/html/2610.02206v1#bib.bib21)\]. While these benchmarks provide valuable insight into what LLMs know and how they behave in integrated workflows, they do not directly evaluate whether models can generate correct invocations of concrete cybersecurity tools in isolation.

This limitation is consequential because modern security operations rely heavily on large, heterogeneous command-line toolchains. Kali Linux, a widely used platform among cybersecurity practitioners, provides access to over 2,000 pre-installed security tool packages \[[31](https://arxiv.org/html/2610.02206v1#bib.bib14)\]. In practice, analysts must translate high-level goals (e.g., “scan this subnet for SMB misconfigurations”) into precise command-line invocations of tools such as Nmap for scanning, Metasploit for exploitation, and Volatility for memory forensics. Although LLMs with function-calling capabilities aim to automate this process, CLIs are unforgiving: minor errors in argument order, flag spelling, alias misuse, or tool misinterpretation can invalidate execution. This motivates a central question: *Can current LLMs reliably translate natural-language security requests into exact, executable CLI commands?*

While function-calling benchmarks for LLMs have matured rapidly \[[17](https://arxiv.org/html/2610.02206v1#bib.bib8), [10](https://arxiv.org/html/2610.02206v1#bib.bib3), [21](https://arxiv.org/html/2610.02206v1#bib.bib12), [20](https://arxiv.org/html/2610.02206v1#bib.bib11), [28](https://arxiv.org/html/2610.02206v1#bib.bib13)\], evaluating cybersecurity tool invocation poses distinct challenges. Existing benchmarks primarily assume schema-defined tools, in which functionality and parameters are explicitly specified via JSON schemas or APIs. In contrast, cybersecurity tooling is dominated by CLIs, such as the Kali Linux toolset, where enumerating hundreds of tool schemas in a model prompt is impractical in typical deployment settings due to context length limitations. As a result, Natural-Language-to-CLI (NL–to–CLI) evaluation is effectively *schema-free*: models must infer appropriate tools and arguments and generate syntactically correct, executable commands rather than populate structured fields.

To address this gap, we develop KaliBench, a fine-grained benchmark for NL–to–CLI cybersecurity tool use on Kali Linux. As shown in Fig. [1](https://arxiv.org/html/2610.02206v1#S0.F1), KaliBench maps analyst intent to exact CLI commands, decomposing tool selection and argument construction for fine-grained, verifiable evaluation. It organizes tools across capability dimensions and security phases and is constructed via a manuscript-grounded pipeline. To ensure data quality, we employ a multi-stage verification process combining LLM-based validation, sandboxed execution, and human-in-the-loop refinement, producing semantically correct and executable commands.

KaliBench provides fine-grained supervision over tool selection and argument construction. We evaluate models under three settings, unrestricted, restricted, and hinted, which vary the degree of tool information provided. This structured formulation further enables *runtime-free verifiable rewards*, allowing training without command execution. Using this framework, we evaluate 24 configurations of general-purpose and security-focused open-weight models and find that performance remains limited, with argument construction as the primary bottleneck. We further show that Supervised Fine-Tuning (SFT) and Reinforcement Learning with Verifiable Rewards (RLVR) improve an 8B model and achieve performance competitive with substantially larger models. Our main contributions are summarized as follows:

- •

  A fine-grained benchmark for schema-free NL-to-CLI evaluation. KaliBench is, to the best of our knowledge, the first benchmark for evaluating LLMs on cybersecurity tool invocation in schema-free CLI settings, comprising 8,504 query–command pairs over 23 capability dimensions and five security phases, split into 5,000 evaluation and 3,504 training samples after deduplication.

- •

  A verified and executable dataset. We construct a high-quality dataset through a multi-stage verification pipeline that ensures both semantic correctness and practical executability.

- •

  Runtime-free verifiable rewards. We show that deterministic CLI structure enables verifiable reward signals without runtime execution, supporting scalable reinforcement learning.

- •

  Fine-grained evaluation and training gains. We evaluate over 20 LLMs under three settings and identify argument construction as the primary bottleneck. Training with supervised fine-tuning and reinforcement learning using KaliBench rewards improves an 8B model’s mean Total Score across the three evaluation modes by 7.5 percentage points.

## 2 Related Work

#### LLMs and Cybersecurity Benchmarks.

Early evaluations of LLMs focused on general-purpose knowledge as measured by MMLU \[[11](https://arxiv.org/html/2610.02206v1#bib.bib4)\]. HELM \[[18](https://arxiv.org/html/2610.02206v1#bib.bib9)\] later introduced a unified evaluation framework that aggregates benchmarks across broader dimensions. Although these evaluations characterize overall language understanding, they do not account for the domain-specific requirements or operational constraints encountered in cybersecurity settings.

As a result, several domain-specific benchmarks have been proposed to evaluate LLMs in cybersecurity contexts. Benchmarks such as SecEval \[[16](https://arxiv.org/html/2610.02206v1#bib.bib7)\], CyberMetric \[[36](https://arxiv.org/html/2610.02206v1#bib.bib16)\], CyberBench \[[19](https://arxiv.org/html/2610.02206v1#bib.bib10)\], SECURE \[[3](https://arxiv.org/html/2610.02206v1#bib.bib2)\], CS-Eval \[[44](https://arxiv.org/html/2610.02206v1#bib.bib20)\], SecBench \[[14](https://arxiv.org/html/2610.02206v1#bib.bib6)\], and CTI-Bench \[[1](https://arxiv.org/html/2610.02206v1#bib.bib1)\] primarily assess cybersecurity knowledge through multiple-choice, true/false, short-answer, or other classification-style questions spanning software and network security, cryptography, industrial control systems, and cyber-threat intelligence. While these benchmarks provide useful insight into models’ conceptual understanding, they largely evaluate knowledge recall and static reasoning rather than concrete operational behavior.

More recent work moves beyond static question answering toward *agentic* evaluation, where models interact with complex environments or autonomously solve multi-step tasks. For example, CyBench \[[45](https://arxiv.org/html/2610.02206v1#bib.bib21)\] and NYU-CTF Bench \[[32](https://arxiv.org/html/2610.02206v1#bib.bib15)\] evaluate LLMs in end-to-end security scenarios via Capture-the-Flag (CTF) challenges, while DefenderBench \[[46](https://arxiv.org/html/2610.02206v1#bib.bib22)\] studies language agents in enterprise-style cybersecurity environments with realistic defensive and offensive workflows. However, end-to-end task performance jointly depends on planning, environment interaction, observation interpretation, tool invocation, and error recovery, making it difficult to attribute failures to individual components. KaliBench complements these benchmarks by isolating command generation and separately evaluating tool selection, optional arguments, and positional arguments.

The benchmark is constructed via LLM-based data generation, multi-round verification-regeneration, and representative-sample selection. #### Function-Calling Benchmarks and Evaluations.

Beyond agentic evaluation, a growing body of work studies LLMs’ ability to invoke external tools through explicit function-calling benchmarks. Benchmarks such as BFCL \[[28](https://arxiv.org/html/2610.02206v1#bib.bib13)\], ToolSandbox \[[21](https://arxiv.org/html/2610.02206v1#bib.bib12)\], StableToolBench \[[10](https://arxiv.org/html/2610.02206v1#bib.bib3)\], and HammerBench \[[38](https://arxiv.org/html/2610.02206v1#bib.bib18)\] evaluate tool use across single-turn, multi-turn, conversational, and agentic settings, emphasizing structured, schema-defined APIs and deterministic validation for general-purpose tool invocation. As a result, these benchmarks assume that tools and parameters are specified through explicit schemas, and do not consider settings where tools must be inferred from a shared CLI. To the best of our knowledge, no existing benchmark directly evaluates natural-language–to–CLI translation for real-world cybersecurity tools under such schema-free conditions, or provides fine-grained, alias-aware assessment of command correctness. KaliBench addresses this gap by enabling systematic evaluation of exact, executable CLI command generation for real-world cybersecurity toolchains.

## 3 KaliBench

[Figure asset](https://arxiv.org/html/2610.02206v1/KaliBench-Sample.svg)

Figure 3: KaliBench Structure and Representative Sample. KaliBench is a structured benchmark of Kali Linux tools organized along the security attack lifecycle. It comprises 5 security phases and 23 functional dimensions. The dataset sample includes natural-language queries and decomposed ground-truth commands. See Appendix [D](https://arxiv.org/html/2610.02206v1#A4) for a detailed view of examples of all 23 dimensions.

KaliBench is a fine-grained benchmark and dataset that serves as a *translation layer* between natural-language cybersecurity queries and executable Kali Linux commands, spanning 1,642 tools and 8,504 query–command pairs. Figure [2](https://arxiv.org/html/2610.02206v1#S2.F2) illustrates the end-to-end pipeline for constructing, verifying, evaluating, and training with KaliBench. The pipeline proceeds in four stages: (1) we extract tool names, flag–value pairs, and documented aliases from official Kali Linux manuscripts, and use them as structured signals to guide LLM-based data generation; (2) generated candidates are iteratively filtered through LLM-based verification, sandboxed terminal execution, and human-in-the-loop evaluation; (3) the verified dataset is deduplicated and split into evaluation and training sets, enabling fine-grained evaluation across multiple metrics and capability dimensions; and (4) using the training split and verifiable reward signals, we demonstrate that parameter efficient post-training with supervised fine-tuning and reinforcement learning significantly improves model performance.

#### 1. Data Generation.

We curate official documentation for Kali Linux tools from the Kali Linux repository \[[15](https://arxiv.org/html/2610.02206v1#bib.bib26)\]. The source corpus comprises 2,372 tools described in structured Markdown, each specifying long and short options and relevant aliases. The documentation also provides a metapackage taxonomy, which we use to annotate each tool with its cybersecurity capability and functional dimension. We process the corpus at the tool level. For each tool, we use Qwen3-Max \[[30](https://arxiv.org/html/2610.02206v1#bib.bib27)\] to generate 10-13 natural-language query–command pairs, along with structured annotations including the tool name, optional arguments as alias-aware flag–value pairs, and positional arguments. These ground-truth command components enable fine-grained analysis of model performance in tool selection, argument construction, and syntactic validity under UNIX shell conventions. Representative examples are shown in Fig. [3](https://arxiv.org/html/2610.02206v1#S3.F3), illustrating the diversity of KaliBench across security phases and functional dimensions. This stage produces 27.7K query–command pairs covering all documented tools. More details about the data generation process can be found in Appendix [B](https://arxiv.org/html/2610.02206v1#A2).

#### 2. Data Verification, Cleaning, and Deduplication.

Despite grounding data generation in official Kali Linux tool manuscripts using a state-of-the-art model (Qwen3-Max), hallucination remains a major challenge. Our initial manual inspection shows that over 50% of generated commands contain hallucinated or misspelled options (e.g., `--silent` instead of `--silence`). To address this issue, we adopt a *multi-stage human-in-loop verification pipeline* that ultimately retains 8,504 high-quality query–command pairs after cleaning and deduplication.

LLM-as-Verifier. We prompt an LLM with the query, the generated_command, and the corresponding tool_manuscript, and task it with verifying (i) whether all flags and arguments are documented, and (ii) whether the command faithfully implements the query using only supported functionality. After the first verification round, 53.8% of generated examples are filtered out. This leaves 413 tools (17.4%) without valid pairs; to preserve coverage, we iteratively regenerate and re-verify the data. The resulting LLM-validated dataset contains 14.5K query–command pairs, with 47.65% of the initial data removed. The prompt details are provided in Appendix [C.2](https://arxiv.org/html/2610.02206v1#A3.SS2).

Terminal Verification. To further ensure the executability of ground-truth commands, we perform system-level validation by executing each LLM-verified command in a controlled sandbox. Specifically, we run each command inside a Docker container provisioned with a *Kali-linux-everything* image and record its outputs, including stdout, stderr, exit code, and execution timeouts. Because command parameters are synthetic (e.g., addresses, devices, paths, and files may not exist in the sandbox), we apply a rule-based filtering pipeline based on observed execution outputs. Commands are rejected when execution logs indicate errors caused by hallucinated tools or invalid arguments that were not detected by the LLM-as-Verifier. This process filters out 11.95% of the LLM-verified commands. Further details of the terminal verification process are provided in Appendix [E](https://arxiv.org/html/2610.02206v1#A5).

Human-in-the-loop Evaluation. As a final verification step, we perform human-in-the-loop evaluation by analyzing model failures in the hinted setting (see the Evaluation Protocol). We focus on cases where even the strongest evaluated model fails to generate a correct command despite having access to tool documentation, as these cases are more likely to reflect issues in the dataset rather than model limitations. We use an AI agent<sup>11</sup> 1 [OpenAI Codex](https://github.com/openai/codex) with [GPT-5.4 Thinking](https://deploymentsafety.openai.com/gpt-5-4-thinking). to produce initial verdicts by cross-checking the semantic alignment among the query, generated command, ground-truth command, and tool documentation. Human reviewers then examine these verdicts to identify query ambiguities and labeling errors. This process reveals that an additional 4.9% of the verified dataset is invalid due to: (a) Malformed CLI options (e.g.,‘--g’ instead of the documented ‘-g’), (b) Omission of arguments explicitly required by the query (e.g., generating ‘\<tool\> completion’ instead of the query-required ‘\<tool\> completion bash’), and (c) Semantic mismatches in argument use (e.g., choosing a flag whose effect does not match the requested operation, swapping the positions of input and output operands, or supplying a filesystem path where the command expects a URL). Detailed cases can be found in Appendix [F](https://arxiv.org/html/2610.02206v1#A6).

Deduplication and Train–test Split. To construct a compact yet semantically diverse evaluation set, we perform *semantic selection* using the SemHash framework \[[37](https://arxiv.org/html/2610.02206v1#bib.bib17)\]. Each record is represented as a semantic unit \[query, tool_name, ground_truth_command\]. Records are embedded into a dense vector space, clustered via approximate nearest-neighbor search, and grouped when pairwise cosine similarity exceeds 0.90. From each cluster, we retain representative examples selected by SemHash. The final cleaned and deduplicated dataset contains 8.5K verified query–command pairs (30.7% of the original 27.7K generated data), forming a high-quality and executable benchmark for NL–to–CLI evaluation. We then sample from this dataset to construct an evaluation set of 5,000 examples (covering all 1,642 tools) and a training set of 3,504 examples (covering 962 tools), prioritizing full tool coverage in the evaluation set while reserving a smaller training split for studying generalization.

#### 3. Evaluation Protocol.

For each query in the evaluation set, models are prompted to generate an executable Kali Linux CLI command under three settings that vary the amount of tool information provided: (1) *Unrestricted*, where the model receives only the natural-language query and must infer both the appropriate tool and its arguments; (2) *Restricted*, where the model is additionally provided with a randomly sampled list of 20 candidate tool names that includes the correct tool, reducing the tool-selection search space while still requiring correct argument construction; and (3) *Hinted*, where the model further receives the official documentation of the candidate tools, approximating schema-based function-calling benchmarks in which tool functionality and parameters are explicitly specified. Details of the structured prompting format and prompt templates are provided in Appendix [C.3](https://arxiv.org/html/2610.02206v1#A3.SS3).

Command Parsing. Model outputs are parsed using Python’s shlex library for lexical analysis of shell-style syntax, enabling faithful emulation of Kali Linux command parsing under UNIX conventions without executing commands. Because KaliBench explicitly records the ground-truth tool_name, optional arguments (as alias-aware flag–value pairs), and ordered positional arguments for each example, we can perform deterministic, component-wise scoring. A CLI command follows the general form \<tool_name\> \<args\>, where arguments are either optional or positional. Optional arguments begin with `--` or `-` and may take values; their order is flexible and aliases are permitted. Positional arguments consist only of values and must appear in a fixed order. See Fig. [3](https://arxiv.org/html/2610.02206v1#S3.F3) for illustration.

Evaluation Metrics. We report a set of fine-grained, component-level metrics, including Tool Accuracy (correct tool selection), Optional-Argument F1 (alias-aware matching of optional flag names), Positional-Argument F1 (multiset matching of positional argument values), Total Score (mean of tool and argument scores), and Exact Correct, which equals 1 only when the tool and all arguments exactly match the ground truth. These metrics enable detailed analysis of model performance across tool selection and argument construction. Details of the metric definitions and calculations are provided in Appendix [L](https://arxiv.org/html/2610.02206v1#A12).

Capability Taxonomy and Security-Phase Annotation. To enable structured, domain-aware analysis beyond raw command correctness, we leverage capability metadata derived from Kali Linux’s official kali-tools metapackage taxonomy, which organizes offensive and defensive tools into 23 functional capability dimensions spanning the full cybersecurity workflow. Inspired by the Lockheed Martin Cyber Kill Chain \[[13](https://arxiv.org/html/2610.02206v1#bib.bib5)\], we group these dimensions into five security phases: *Reconnaissance & Initial Access* (information-gathering, 802-11, rfid, bluetooth, sdr, social-engineering), *Vulnerability Analysis* (vulnerability, fuzzing, web, database, voip), *Exploitation & Payload Delivery* (exploitation, sniffing-spoofing, hardware, wireless), *Post-Exploitation & Lateral Movement* (post-exploitation, passwords, windows-resources, crypto-stego), and *Defensive Analysis & Reporting* (reverse-engineering, forensics, reporting, gpu). Although some capabilities span multiple stages, each dimension is assigned a primary functional role for clarity, enabling aggregation of evaluation metrics across coherent capability dimensions and security phases and supporting systematic analysis of model performance in natural-language–to–CLI translation across different cybersecurity contexts.

#### 4. Training Protocol.

Our training data support LLM post-training via Supervised Fine-Tuning (SFT) and Reinforcement Learning with Verifiable Rewards (RLVR). We adopt the same prompt template used during evaluation, with the query, a randomly sampled list of candidate tools, and tool documentation as inputs. We concatenate data from all three evaluation settings, resulting in $3{,}504\times 3=10{,}512$ training samples. Additional details are provided in Appendix [G.2](https://arxiv.org/html/2610.02206v1#A7.SS2).

![Refer to caption](https://arxiv.org/html/2610.02206v1/train_pipe.png)

Figure 4: KaliBench Training Protocol.

SFT. We use the constructed prompt template and treat the ground-truth command as the target output. The model is trained to generate the correct command given the query and optional tool information.

RLVR. We extend the prompt template by instructing the model to produce intermediate reasoning within *\<think\>…\</think\>* tags before generating the final command, following \[[9](https://arxiv.org/html/2610.02206v1#bib.bib35)\]. Our reward function is derived from component-level evaluation metrics, providing fully verifiable signals for accurate prediction of tool name, positional arguments, and alias-aware optional arguments. This enables fine-grained learning signals beyond a binary exact-match objective. An additional reward is assigned for exact command matches. Because ground-truth commands are validated during data construction via sandboxed execution, rewards can be computed without executing model outputs, enabling efficient RL without runtime. We include a formatting reward to enforce output structure.

## 4 Experiments

#### Experiment Setup.

All evaluations of open-source models were conducted on an NVIDIA A100 multi-GPU cluster using the vLLM inference engine, with selected large models evaluated via external APIs<sup>22</sup> 2 OpenRouter: <https://openrouter.ai/>. We evaluate 14 general-purpose models: Llama3.1-Instruct (8B) \[[8](https://arxiv.org/html/2610.02206v1#bib.bib29)\], Qwen-3 (8B, 32B; with and without reasoning) \[[41](https://arxiv.org/html/2610.02206v1#bib.bib33)\], Mistral-3.2 (24B) \[[23](https://arxiv.org/html/2610.02206v1#bib.bib37)\], Gemma-3 (27B) \[[35](https://arxiv.org/html/2610.02206v1#bib.bib34)\], GPT-OSS (20B, 120B) \[[24](https://arxiv.org/html/2610.02206v1#bib.bib36)\], LLaMA-3.3-Instruct (70B) \[[22](https://arxiv.org/html/2610.02206v1#bib.bib38)\], Qwen-2.5-Instruct (72B) \[[29](https://arxiv.org/html/2610.02206v1#bib.bib40)\], Qwen3-Coder-Next (80B) \[[4](https://arxiv.org/html/2610.02206v1#bib.bib39)\], and DeepSeek-V3.2 (685B) \[[6](https://arxiv.org/html/2610.02206v1#bib.bib41)\], GLM-5.2 (753B) \[[7](https://arxiv.org/html/2610.02206v1#bib.bib42)\] along with 7 cybersecurity-oriented models: Foundation-Sec-Instruct (8B) \[[39](https://arxiv.org/html/2610.02206v1#bib.bib28)\], Foundation-Sec-Reasoning (8B) \[[42](https://arxiv.org/html/2610.02206v1#bib.bib31)\], Llama-Primus-Base/Merged (8B) and Llama-Primus-Nemotron (70B) \[[43](https://arxiv.org/html/2610.02206v1#bib.bib30)\], and RedSage-Ins/DPO (8B) \[[34](https://arxiv.org/html/2610.02206v1#bib.bib32)\], as well as three variants of a cybersecurity-oriented model further fine-tuned on KaliBench. Models with 72B or more parameters were evaluated through the OpenRouter API; all other models are obtained from their official Hugging Face repositories under their respective licenses and evaluated under a fixed inference configuration; details are in Appendix [G.1](https://arxiv.org/html/2610.02206v1#A7.SS1).

#### Training Setup.

We employ parameter-efficient fine-tuning using LoRA \[[12](https://arxiv.org/html/2610.02206v1#bib.bib23)\] with Unsloth \[[5](https://arxiv.org/html/2610.02206v1#bib.bib24)\]. We select the best-performing 8B cybersecurity-tuned model RedSage-Ins as the backbone. Using the training dataset described in Sec. [3](https://arxiv.org/html/2610.02206v1#S3.SS0.SSS0.Px4), we train three variants, collectively referred to as RedSage-K: (1) SFT, (2) RLVR with Group Relative Policy Optimization (GRPO) \[[33](https://arxiv.org/html/2610.02206v1#bib.bib25)\], and (3) SFT followed by GRPO (SFT+GRPO). All models are trained on a single H200 GPU (141GB VRAM) with a total batch size of 32 for two epochs; details are in Appendix [G.2](https://arxiv.org/html/2610.02206v1#A7.SS2).

### 4.1 Model Performance Across Three Modes

Table [1](https://arxiv.org/html/2610.02206v1#S3.T1) summarizes per-model performance under three modes: Unrestricted (U), Restricted (R), and Hinted (H). We report Exact Correct (EC), Tool Accuracy (TA), Optional-Argument F1 (Opt-F1), Positional-Argument F1 (Pos-F1), Total Score (TS), and Average TS (Avg.). We analyze key patterns with respect to tool information, model type and scale, and post-training on KaliBench.

#### Impact of Evaluation Modes.

The three evaluation modes reveal a clear separation between tool selection and argument construction. Transitioning from U to R substantially improves TA (72.0%$\rightarrow$95.2% on average), indicating that constraining the candidate tool space largely resolves tool-selection errors. However, this shift yields only modest gains in Opt-F1, Pos-F1, and EC, indicating that correct tool selection alone does not ensure accurate argument generation. The metric averages further reveal a hierarchy of difficulty: optional-argument prediction is the most challenging, followed by positional-argument prediction. In contrast, H produces the largest improvements, increasing Opt-F1 from 45.1% to 87.8%, Pos-F1 from 61.1% to 90.1%, TS from 59.4% to 90.8%, and EC from 22.3% to 73.1%. These gains indicate that tool hints resolve ambiguities in argument selection, ordering, and formatting, and suggest that existing models lack sufficient domain knowledge to construct accurate commands without tool documentation. Overall, R primarily improves *which* tool to use, whereas H improves *how* the command is constructed; without hints, open-weight models still struggle with accurate argument generation, the primary bottleneck.

#### Impact of Model Type and Scale.

Cybersecurity-oriented models (<sup>⋆</sup>) do not consistently outperform strong general-purpose models on query-to-command generation, but their advantages become more apparent in less-guided settings. In the compact regime, RedSage-Ins<sup>⋆</sup> achieves higher TS than non-thinking Qwen3 in both U and R (56.4% vs. 55.5% and 69.3% vs. 68.2%), suggesting that domain-specific training provides useful priors when models must infer command structure with limited support. In contrast, general-purpose models perform better in H, where Qwen3 surpasses RedSage-Ins<sup>⋆</sup> (91.6% vs. 89.5%), indicating stronger instruction-following and context utilization under richer guidance. Overall, cybersecurity-oriented models are more effective in under-specified settings, while general-purpose models better exploit explicit hints. Reasoning-enabled variants (<sup>†</sup>) further improve argument-level performance, particularly in Opt-F1, Pos-F1, and EC. For example, Qwen3<sup>†</sup> improves Avg from 71.8% to 73.8% over Qwen3 and achieves strong H-mode results (94.0% TS, 80.9% EC), highlighting the role of reasoning in intent decomposition and context utilization. Finally, while performance generally improves with scale, gains are uneven. For example, Qwen3<sup>†</sup> (8B) outperforms larger models, including Gemma-3-it (27B) and Llama-Primus-Ins<sup>⋆</sup> (70B), in Avg. These results suggest that effective NL–to–CLI generation depends on domain knowledge, instruction-following, reasoning, and task alignment, rather than scale alone.

#### Proprietary Models and Scaffolded Inference.

Our main evaluation emphasizes open-weight models because local deployment is particularly important in cybersecurity, where queries, target information, and operational data may be sensitive and cannot always be shared with proprietary APIs. To assess whether KaliBench remains challenging for stronger proprietary models and scaffolded systems, we additionally evaluate GPT-5.6-Sol \[[27](https://arxiv.org/html/2610.02206v1#bib.bib43)\], Claude Opus 5 \[[2](https://arxiv.org/html/2610.02206v1#bib.bib45)\], and OpenAI Codex  \[[25](https://arxiv.org/html/2610.02206v1#bib.bib44)\], powered by GPT-5.5 \[[26](https://arxiv.org/html/2610.02206v1#bib.bib46)\] with xhigh reasoning effort. We evaluate all systems on the 5,000 test queries in the Unrestricted setting.

EC (Exact Correct) is computed over answered queries; the EC (all 5K) counts blocked or missing outputs as incorrect. For Codex, we use its scaffolded CLI workflow and score only the final submitted command.

As shown in Table [2](https://arxiv.org/html/2610.02206v1#S4.T2), GPT-5.6-Sol achieves the highest full-set Exact Correct of 61.68%, followed by Codex at 51.68% and Claude Opus 5 at 44.02%. All three outperform GLM-5.2, the strongest evaluated open-weight model in this setting, which achieves 41.32%. Response coverage, however, varies across systems: GPT-5.6-Sol answers 4,988 of 5,000 queries, compared with 4,633 for Codex and 3,675 for Claude Opus 5. These coverage differences suggest that provider-specific safety restrictions influence cybersecurity-related usage. For example, Claude Opus 5 achieves 59.89% EC on answered queries but answers only 73.50% of the test set, reducing its full-set EC to 44.02%. Moreover, despite the gains over open-weight models, the highest full-set accuracy among these systems is 61.68%, indicating that KaliBench remains unsaturated and that exact command generation is challenging. Complete metrics and reporting details are provided in Appendix [M](https://arxiv.org/html/2610.02206v1#A13).

#### Impact of KaliBench Post-training.

Post-training on the KaliBench training split substantially improves compact models. The three RedSage-K variants achieve Avg scores of 76.9, 77.4, and 79.2, with RedSage-K (SFT+GRPO) ranking third in Avg among all evaluated open-weight models, only 1.0 point below DeepSeek-V3.2<sup>†</sup> despite using an 8B backbone. The methods exhibit complementary strengths: RedSage-K (SFT) attains the best compact-model TA across all modes, shows stronger gains in Opt-F1, and delivers the largest improvements in H, suggesting that supervised fine-tuning effectively learns tool mapping and benefits from contextual hints. In contrast, RedSage-K (GRPO) shows stronger gains in Pos-F1 and TS under U and R, but is weaker in H.

Combining both methods, RedSage-K (SFT+GRPO) yields the best compact-model U/R TS and EC, demonstrating the benefit of combining SFT and RLVR under limited guidance. However, RedSage-K (GRPO) and RedSage-K (SFT+GRPO) slightly reduce H-mode TS relative to the original RedSage-Ins model. Our paired analysis identifies argument-construction errors and regressions on previously solved examples, with SFT initialization mitigating these regressions (Appendix [I](https://arxiv.org/html/2610.02206v1#A9)). Overall, KaliBench post-training enables compact models to approach larger ones in cybersecurity tool use under less-guided settings.

### 4.2 Fine-Grained Performance and Robustness Analysis

#### Dimension-wise and Tool-level Analysis.

Figure [5](https://arxiv.org/html/2610.02206v1#S4.F5)(a) reports TS performance across 23 capability dimensions, five security phases, and three evaluation modes, aggregated over all evaluated models. Performance varies across dimensions, but relative difficulty remains broadly consistent across modes, suggesting that additional tool information improves overall scores without fundamentally changing which dimensions are harder. Dimensions such as gpu and crypto-stego consistently achieve higher scores, whereas 802-11 and wireless show lower minima, especially in U and R modes. We also observe mode-specific deviations, such as hardware in H mode, where performance remains comparatively lower, likely reflecting the difficulty of longer or more complex tool descriptions.

From a distributional perspective, variability decreases as tool information increases. The U mode shows the widest spread across models, reflecting high variance without tool guidance; R reduces this variability by constraining tool selection; and H further stabilizes performance across most dimensions. However, H narrows variance without eliminating dimension-level gaps, suggesting that documentation improves argument construction but does not fully resolve interface complexity. At the phase level, Reconnaissance and Vulnerability Analysis are relatively stable, while Post-Exploitation and Defensive Analysis show greater variation, likely due to more heterogeneous CLI structures.

At the tool level, performance differences largely reflect CLI interface complexity. Tools with simple invocation patterns and well-defined defaults (e.g., truecrypt2john, jsql) are handled reliably, whereas those with irregular or uncommon options (e.g., nikto, hashrat) remain challenging due to precise flag–value binding and strict syntax. Additional full statistics are provided in Appendix [K](https://arxiv.org/html/2610.02206v1#A11), confirming that tool-level difficulty is driven more by interface complexity than model-specific limitations.

#### Mode-wise Performance Trends.

Figure [5](https://arxiv.org/html/2610.02206v1#S4.F5)(b,c) visualizes the distributions of Total Score and Exact Correct across the three evaluation modes. Both metrics improve consistently from U to R to H, with H achieving the strongest results. This supports our earlier finding that tool documentation provides the largest gains, primarily by improving argument prediction, the main bottleneck in accurate command construction.

The two metrics exhibit different patterns of cross-model dispersion. The Total Score range narrows from 21.8 $\rightarrow$ 18.4 $\rightarrow$ 13.7 percentage points across U, R, and H. In contrast, the Exact Correct range remains wide at 28.8, 33.8, and 28.3 percentage points, respectively. This suggests that providing tool information brings models closer together in Total Score, while substantial differences in exact command correctness persist.

#### Common Failure Pattern Analysis.

Weak query-to-command performance primarily stems from accumulated errors in command construction, particularly with optional arguments. Across models, we observe four recurring patterns: (i) long–short option misuse, where alias forms are mixed (e.g., `--`domain/`-`d), producing invalid commands; (ii) option hallucination, where positional arguments are treated as flags or nonexistent aliases inferred (e.g., ‘st `--`client’); (iii) hallucinated long options, where tools with only short flags lead to invented long forms; and (iv) erroneous option names, where singular–plural confusion produces incorrect variants (e.g., `--`symlink vs. `--`symlinks).

#### Robustness to Query Variation.

Since KaliBench queries are synthesized from tool documentation, we examine the sensitivity of model performance to changes in query wording and presentation. We evaluate eight model configurations under three query variations: Paraphrase (uses synonyms and alternative phrasing); Informal (adopts conversational wording); and Messy (introduces linguistic and formatting noise, such as grammatical errors, omitted prepositions or verbs, and incorrect word choices).

Table [3](https://arxiv.org/html/2610.02206v1#S4.T3) shows that paraphrases have little overall effect and slightly improve performance in the Unrestricted and Restricted settings. Informal queries introduce a small but consistent degradation. Messy queries cause the largest drop across all settings, especially in the Unrestricted setting. Hinted mode shows the smallest decline under messy inputs (1.07 percentage points), suggesting that access to full tool documentation mitigates, but does not eliminate, the impact of noisy wording. The eight configurations and their model-level results for the Messy variation are detailed in Appendix [N](https://arxiv.org/html/2610.02206v1#A14).

## 5 Discussion and Conclusion

KaliBench exposes a clear gap between LLMs’ general cybersecurity knowledge and their ability to generate exact, executable CLI commands. Our results show that tool selection and argument construction are fundamentally different challenges: restricting candidate tools largely resolves tool-selection errors, while argument-level correctness, especially for optional flags and flag–value bindings, remains the primary bottleneck. Providing tool documentation results in the largest gains, indicating that failures often stem from limited domain knowledge rather than intent understanding. These findings highlight the importance of evaluating tool use at the command-structure level in schema-free settings, where models must infer tools and syntax without explicit APIs.

Beyond evaluation, KaliBench enables effective model improvement through fine-grained, runtime-free verifiable rewards. Post-training with SFT and RLVR substantially improves compact models, allowing an 8B model to approach much larger systems. Despite these advances, limitations remain, including the focus on single-turn command generation and reliance on documentation-grounded data. Future work should extend to multi-step workflows, retrieval-augmented tool use, and environment-aware evaluation. Overall, KaliBench provides a practical benchmarking and training framework for advancing the reliable and executable use of LLM-based cybersecurity tools.

## NeurIPS Paper Checklist

1.  1\.

    Claims

2.  Question: Do the main claims made in the abstract and introduction accurately reflect the paper’s contributions and scope?

3.  Answer: \[Yes\]

4.  Justification: Our paper’s Abstract and Section 1: Introduction clearly define the article’s contributions and scope.

5.  Guidelines:

    - •

      The answer \[N/A\] means that the abstract and introduction do not include the claims made in the paper.

    - •

      The abstract and/or introduction should clearly state the claims made, including the contributions made in the paper and important assumptions and limitations. A \[No\] or \[N/A\] answer to this question will not be perceived well by the reviewers.

    - •

      The claims made should match theoretical and experimental results, and reflect how much the results can be expected to generalize to other settings.

    - •

      It is fine to include aspirational goals as motivation as long as it is clear that these goals are not attained by the paper.

6.  2\.

    Limitations

7.  Question: Does the paper discuss the limitations of the work performed by the authors?

8.  Answer: \[Yes\]

9.  Justification: We carefully discuss the limitations of our work in Appendix [O](https://arxiv.org/html/2610.02206v1#A15): Limitations.

10. Guidelines:

    - •

      The answer \[N/A\] means that the paper has no limitation while the answer \[No\] means that the paper has limitations, but those are not discussed in the paper.

    - •

      The authors are encouraged to create a separate “Limitations” section in their paper.

    - •

      The paper should point out any strong assumptions and how robust the results are to violations of these assumptions (e.g., independence assumptions, noiseless settings, model well-specification, asymptotic approximations only holding locally). The authors should reflect on how these assumptions might be violated in practice and what the implications would be.

    - •

      The authors should reflect on the scope of the claims made, e.g., if the approach was only tested on a few datasets or with a few runs. In general, empirical results often depend on implicit assumptions, which should be articulated.

    - •

      The authors should reflect on the factors that influence the performance of the approach. For example, a facial recognition algorithm may perform poorly when image resolution is low or images are taken in low lighting. Or a speech-to-text system might not be used reliably to provide closed captions for online lectures because it fails to handle technical jargon.

    - •

      The authors should discuss the computational efficiency of the proposed algorithms and how they scale with dataset size.

    - •

      If applicable, the authors should discuss possible limitations of their approach to address problems of privacy and fairness.

    - •

      While the authors might fear that complete honesty about limitations might be used by reviewers as grounds for rejection, a worse outcome might be that reviewers discover limitations that aren’t acknowledged in the paper. The authors should use their best judgment and recognize that individual actions in favor of transparency play an important role in developing norms that preserve the integrity of the community. Reviewers will be specifically instructed to not penalize honesty concerning limitations.

    Theory Assumptions and Proofs

12. Question: For each theoretical result, does the paper provide the full set of assumptions and a complete (and correct) proof?

13. Answer: \[N/A\]

14. Justification: The contributions of this paper focus on experimental results rather than theoretical derivations and theoretical results.

15. Guidelines:

    - •

      The answer \[N/A\] means that the paper does not include theoretical results.

    - •

      All the theorems, formulas, and proofs in the paper should be numbered and cross-referenced.

    - •

      All assumptions should be clearly stated or referenced in the statement of any theorems.

    - •

      The proofs can either appear in the main paper or the supplemental material, but if they appear in the supplemental material, the authors are encouraged to provide a short proof sketch to provide intuition.

    - •

      Inversely, any informal proof provided in the core of the paper should be complemented by formal proofs provided in appendix or supplemental material.

    - •

      Theorems and Lemmas that the proof relies upon should be properly referenced.

16. 4\.

    Experimental result reproducibility

17. Question: Does the paper fully disclose all the information needed to reproduce the main experimental results of the paper to the extent that it affects the main claims and/or conclusions of the paper (regardless of whether the code and data are provided or not)?

18. Answer: \[Yes\]

19. Justification: We disclose the full code and data in the link of our project page (Abstract). In addition, the experiments in this paper evaluate multiple open-source models and utilize the vLLM engine during the inference phase; these settings ensure the standardization and reproducibility of the experiments (Section 4: Experiments). More specifically, Appendix B: CLI Command Generation and Appendix C: Prompt Templates provide all the prompts needed to reproduce the generation of the benchmark data, while Appendix E: Terminal verification Details provides the rules for sample-wise terminal verification, and Appendix [L](https://arxiv.org/html/2610.02206v1#A12): Details about Metrics Calculation details the metric calculations required to accurately reproduce the result.

20. Guidelines:

    - •

      The answer \[N/A\] means that the paper does not include experiments.

    - •

      If the paper includes experiments, a \[No\] answer to this question will not be perceived well by the reviewers: Making the paper reproducible is important, regardless of whether the code and data are provided or not.

    - •

      If the contribution is a dataset and/or model, the authors should describe the steps taken to make their results reproducible or verifiable.

    - •

      Depending on the contribution, reproducibility can be accomplished in various ways. For example, if the contribution is a novel architecture, describing the architecture fully might suffice, or if the contribution is a specific model and empirical evaluation, it may be necessary to either make it possible for others to replicate the model with the same dataset, or provide access to the model. In general. releasing code and data is often one good way to accomplish this, but reproducibility can also be provided via detailed instructions for how to replicate the results, access to a hosted model (e.g., in the case of a large language model), releasing of a model checkpoint, or other means that are appropriate to the research performed.

    - •

      While NeurIPS does not require releasing code, the conference does require all submissions to provide some reasonable avenue for reproducibility, which may depend on the nature of the contribution. For example

      1.  \(a\)

          If the contribution is primarily a new algorithm, the paper should make it clear how to reproduce that algorithm.

      2.  \(b\)

          If the contribution is primarily a new model architecture, the paper should describe the architecture clearly and fully.

      3.  \(c\)

          If the contribution is a new model (e.g., a large language model), then there should either be a way to access this model for reproducing the results or a way to reproduce the model (e.g., with an open-source dataset or instructions for how to construct the dataset).

      4.  \(d\)

          We recognize that reproducibility may be tricky in some cases, in which case authors are welcome to describe the particular way they provide for reproducibility. In the case of closed-source models, it may be that access to the model is limited in some way (e.g., to registered users), but it should be possible for other researchers to have some path to reproducing or verifying the results.

    Experiment Statistical Significance

32. Question: Does the paper report error bars suitably and correctly defined or other appropriate information about the statistical significance of the experiments?

33. Answer: \[Yes\]

34. Justification: The paper provides information about variability through distributional statistics. In particular, Figure 5 reports box plots (Q1–Q3 with min/max whiskers) across all models, security dimensions, and mode settings.

35. Guidelines:

    - •

      The answer \[N/A\] means that the paper does not include experiments.

    - •

      The authors should answer \[Yes\] if the results are accompanied by error bars, confidence intervals, or statistical significance tests, at least for the experiments that support the main claims of the paper.

    - •

      The factors of variability that the error bars are capturing should be clearly stated (for example, train/test split, initialization, random drawing of some parameter, or overall run with given experimental conditions).

    - •

      The method for calculating the error bars should be explained (closed form formula, call to a library function, bootstrap, etc.)

    - •

      The assumptions made should be given (e.g., Normally distributed errors).

    - •

      It should be clear whether the error bar is the standard deviation or the standard error of the mean.

    - •

      It is OK to report 1-sigma error bars, but one should state it. The authors should preferably report a 2-sigma error bar than state that they have a 96% CI, if the hypothesis of Normality of errors is not verified.

    - •

      For asymmetric distributions, the authors should be careful not to show in tables or figures symmetric error bars that would yield results that are out of range (e.g., negative error rates).

    - •

      If error bars are reported in tables or plots, the authors should explain in the text how they were calculated and reference the corresponding figures or tables in the text.

## Appendix B CLI Command Generation

KaliBench focuses on deterministic natural-language-to-CLI translation at scale within Kali Linux ($\sim$2,372 tools). It defines reviewer-checkable canonicalization rules that specify:

1.  i\.

    Ordering: the command begins with the tool name, followed by all long flags, then all short flags (lexicographically), then flags with values, and finally positional arguments in document order.

2.  ii\.

    Flag syntax: flags and their values are space-separated (e.g., ‘`--`opt value’, ‘-s value’). Equals-style bindings (e.g., ‘`--`opt=value’) are allowed. Boolean flags take no value.

3.  iii\.

    Quoting and aliasing: quoting is applied only when required (e.g., values containing whitespace or shell meta-characters). Aliases (e.g., ‘`--`help’ vs. ‘-h’) are normalized, but the model must output a single canonical form—preferably the long-flag variant.

To ensure unambiguous extraction, all CLI predictions are enclosed within a standardized \<output\> \</output\> tag. This enables robust isolation and symbolic comparison of the core command.

In all, these constraints enable scalable and accurate evaluation by supporting diverse arguments and alias combinations in the data generation process, ensuring reproducibility through exact parse-tree matching.\

## Appendix E Terminal verification Details

We perform sample-wise terminal verification by executing each ground_truth_command in a controlled Docker sandbox (with Kali Linux environment). For each command, we create an isolated working directory to avoid side effects, and run it via subprocess with a fixed timeout and resource limits. During execution, we capture stdout, stderr, exit_code, and runtime signals.

After execution, we assign labels based on simple rules:

- •

  PASS_EXECUTED: exit code = 0

- •

  TIMEOUT: command exceeds time limit

- •

  REJECT_HALLUCINATED_TOOL: tool not found (e.g., exit code 127 or error patterns)

- •

  REJECT_HALLUCINATED_PARAMETER: invalid or unsupported options detected from error messages

- •

  PASS_RUNTIME_ERROR: non-zero exit code without clear hallucination signals

We use regex-based pattern matching on stderr/stdout to detect tool and parameter errors, ensuring that obvious hallucinations can be filtered out even if the command executes.

A brief Pseudo-code can further show our execution process:


    # Input: JSONL dataset of query–command pairs
    # Output: execution logs with classification labels
    for each row in dataset:
        # 1. Prepare command
        cmd = row["ground_truth_command"]

        # 2. Create isolated sandbox
        workdir = create_sandbox(cmd)

        # 3. Execute command with timeout
        result = run(cmd, timeout=20s, in workdir)
        stdout, stderr = result.stdout, result.stderr
        exit_code = result.exit_code

        # 4. Classify execution outcome
        if result.timed_out:
            label = TIMEOUT

        elif exit_code == 127 or match(tool_error_pattern, stderr, stdout):
            label = REJECT_HALLUCINATED_TOOL

        elif match(parameter_error_pattern, stderr, stdout):
            label = REJECT_HALLUCINATED_PARAMETER

        elif exit_code == 0:
            label = PASS_EXECUTED

        else:
            label = PASS_RUNTIME_ERROR

        # 5. Save execution log
        save {
            command, stdout, stderr,
            exit_code, label, workdir
        }

This process filters out commands with hallucinated tools or invalid parameters, while retaining executable commands and partially valid ones that are syntactically correct but may fail at runtime due to placeholder inputs (e.g., using non-existent targets such as curl https://example.com).

## Appendix F Representative Invalid Cases Identified During Manual Review

To further substantiate the error types summarized in the main text, we provide representative invalid cases identified during manual review.

#### (a) Malformed CLI options.

For the query “Launch debug_me via qemu-aarch64_be and wait for a GDB connection on port 1234,” the correct command is “qemu-aarch64_be -g 1234 debug_me”, whereas the annotated ground truth uses the malformed option --g instead of -g.

#### (b) Omission of query-required arguments.

For the query “Generate shell completion script for kustomize so it can be used with bash,” the correct command is “kustomize completion bash”, but the annotated ground truth uses only “kustomize completion” and omits the shell argument, which is specifically asked by the query.

#### (c) Semantic mismatches in argument use.

We observe three common subtypes. First, the annotated command may use a flag with the wrong function: for the query “Run Git with the working directory set to /home/user/project,” the correct command is “git -C /home/user/project status”, while the ground truth uses work-tree, which changes the repository work tree rather than the working directory. Second, the annotated command may reverse operand order: for the query “converting mac.txt to unix3.txt”, the correct form is dos2unix -n mac.txt unix3.txt, while the ground truth swaps input and output. Third, the annotated command may use the wrong argument type: for the query "Execute svnsync’s ’sync’ subcommand on the local mirror located at ’/srv/svn/replica’", the correct command is "svnsync sync file:///srv/svn/replica", while the ground truth supplies the plain path “/srv/svn/replica” where a URL is required.

### G.2 Training Setup.

We fine-tuned RedSage-Qwen3-8B-Ins using parameter-efficient LoRA adapters on a single NVIDIA H200 GPU. For both SFT and GRPO training, we used LoRA rank 64, LoRA alpha 128, and zero LoRA dropout, applying adapters to the attention and MLP projection layers: q_proj, k_proj, v_proj, o_proj, gate_proj, up_proj, and down_proj. Training used bfloat16 precision, gradient checkpointing, and the 8-bit AdamW optimizer with learning rate $5\times 10^{-6}$, weight decay $10^{-3}$, Adam betas $(0.9,0.999)$, gradient clipping at 1.0, and a linear learning-rate schedule with 10% warmup. We trained for 2 epochs. The software stack included Transformers 4.57.6, Unsloth 2026.4.6, PEFT 0.19.1, and Python 3.12.13.

For the SFT model, we trained from the RedSage-Qwen3-8B-Ins checkpoint with a per-device batch size of 4 and gradient accumulation of 8, giving an effective batch size of 32. The maximum sequence length was 16,384 tokens, with packing disabled and padding-free training enabled. The SFT objective used the standard negative log-likelihood loss. SFT training required $\sim$32 minutes.

For the GRPO-trained model, we used the same optimizer, LoRA, precision, and batch settings as SFT. GRPO used 8 generations per prompt, a generation batch size of 32, and group-based reward scaling. The maximum prompt length was 5,549 tokens, and the maximum completion length was 6,739 tokens. We used the BNPO-style GRPO loss with clipping parameter $\epsilon=0.2$ and KL coefficient $\beta=0.001$. Generation during GRPO was accelerated with colocated vLLM, using tensor parallel size 1 and GPU memory utilization 0.3. GRPO training required $\sim$28 hours when initialized directly from RedSage-Qwen3-8B-Ins, and $\sim$17 hours when initialized from our SFT checkpoint.

## Appendix H Model Performance Difference across Execution Modes

Table [5](https://arxiv.org/html/2610.02206v1#A7.T5) provides a model-wise decomposition of performance changes across execution modes, complementing the raw-score analysis in Table [1](https://arxiv.org/html/2610.02206v1#S3.T1).

A consistent pattern is that improvements in tool selection do not propagate proportionally to exact command correctness. Although Tool $\Delta_{1}$ is large across all models (23.2 pp on average), Exact $\Delta_{1}$ remains much smaller (5.9 pp on average). This indicates that even if the tool name can be settled, the remaining errors are still dominated by argument selection, value binding, and command formatting. Thus, restricted mode mainly reduces tool-choice ambiguity, but does not substantially solve command construction.

The restricted-to-hinted transition shows the opposite behavior. Tool $\Delta_{2}$ is small, unstable, and often negative: 11 out of 24 models show degraded Tool Accuracy after adding full tool manuscripts, with Gemma-3-it-27B dropping by 10.3 pp. In contrast, argument-related metrics improve substantially, with Optional F1 increasing by about 39.1 pp and Positional F1 by about 21.9 pp on average. This asymmetry suggests that tool manuscripts are not primarily useful for identifying tools; instead, they help models resolve optional-argument ambiguity, flag selection, value specification, and positional ordering.

Exact Correct further confirms this mechanism. Exact $\Delta_{2}$ averages 44.8 pp, nearly eight times larger than Exact $\Delta_{1}$, showing that argument correction is far more effective than tool disambiguation for producing fully correct commands. Model-wise, the largest Exact gains are more closely associated with large Optional $\Delta_{2}$ than with large Tool $\Delta_{1}$, suggesting that optional-argument modeling is the key factor determining whether partial command understanding becomes exact command reconstruction.

The RedSage-K variants show a distinct delta pattern: despite strong raw performance in the U and R settings, they benefit less from mode switching than many baselines. In particular, RedSage-K (GRPO) and RedSage-K (SFT+GRPO) exhibit smaller Optional, Positional, Total, and Exact $\Delta$s than strong general-purpose models. This suggests that KaliBench post-training improves intrinsic command understanding, but the RedSage-K variants may be less effective at exploiting full tool documentation, consistent with their weaker Hinted-mode gains in the main results.

Overall, the delta analysis shows that NL-to-CLI errors are not reduced uniformly across components. The main model-wise differentiator is not the magnitude of tool-selection gains, but how efficiently models use documentation to repair argument errors and produce exact commands.

## Appendix L Details about Metrics Calculation

### L.1 Command-level Scoring for Evaluating Models

For each example, we extract the predicted command from the \<output\> tag and parse both the ground-truth and predicted commands into: \<tool name\>, \<optional flags\>, and \<positional arguments\> to know which flags take values and which flags are aliases.

#### Tool score

Tool_score is a binary indicator: it is 1 if the predicted tool name exactly matches the ground-truth tool name, and 0 otherwise.

#### Optional-argument F1.

Ground-truth optional flags are grouped into alias sets (e.g., ‘-h’ \| ‘`--`help’). A predicted flag is counted as correct for a group if it matches any alias in that group. Let $G$ be the number of ground-truth groups, $N_{\text{pred}}$ be the total number of predicted optional flags, and $H$ be the number of ground-truth groups that are “hit” by at least one predicted alias. We define $\text{precision}_{\text{opt}}=H/N_{\text{pred}}$ and $\text{recall}_{\text{opt}}=H/G$, and compute

|     |                |     |
|-----|----------------|-----|
|     | $$\text{optional\_f1}=\frac{2\times\text{precision}_{\text{opt}}\times\text{recall}_{\text{opt}}}{\text{precision}_{\text{opt}}+\text{recall}_{\text{opt}}}.$$ |     |

If both ground truth and prediction have no optional flags, we set optional_f1 to 1; if ground truth command has no optional flags while the predicted command has, we set it to 0.

#### Positional-argument F1.

The ground-truth and predicted positional arguments form 2 sets. We match each predicted argument to an identical ground-truth argument at most once: every successful match counts as a true positive $TP$; any remaining unmatched predicted arguments are false positives $FP$; and any remaining unmatched ground-truth arguments are false negatives $FN$. We then define $\text{precision}_{\text{pos}}=TP/(TP+FP)$ and $\text{recall}_{\text{pos}}=TP/(TP+FN)$, and compute

|     |                |     |
|-----|----------------|-----|
|     | $$\text{positional\_f1}=\frac{2\,\text{precision}_{\text{pos}}\,\text{recall}_{\text{pos}}}{\text{precision}_{\text{pos}}+\text{recall}_{\text{pos}}}.$$ |     |

If both lists are empty, we set positional_f1 to 1; if exactly one is empty, we set it to 0.

#### Total score and Exact match

Total score is the average of tool score, optional f1 and positional f1. And Exact match evaluates end-to-end command correctness which is 1 for generating a correct canonicalized command, and 0 for any error in parameters.

### L.2 Dimensional Score Calculation

To analyze model performance across functional security domains, we leverage Kali’s metapackage taxonomy (Section [3](https://arxiv.org/html/2610.02206v1#S3.SS0.SSS0.Px3)) to assign each tool to one or more of $D=23$ capability dimensions. Each query–command pair is therefore annotated with a multi-hot vector $\mathbf{v}^{(i)}\in\{0,1\}^{D}$ indicating the dimensions to which its ground-truth tool belongs.

For each evaluation instance $i$, we project its scalar prediction score $s^{(i)}\in[0,1]$ onto the corresponding capability dimensions by element-wise multiplication:

|     |                |     |
|-----|----------------|-----|
|     | $$\mathbf{s}^{(i)}=s^{(i)}\cdot\mathbf{v}^{(i)}.$$ |     |

This assigns the score $s^{(i)}$ to all dimensions associated with the tool, while all other dimensions receive zero. Summing $\mathbf{s}^{(i)}$ over all instances yields per-dimension performance scores for each model, enabling fine-grained analysis across the 23 cybersecurity capability dimensions.

#### Example.

Consider a tool that is associated with three capability dimensions in Kali’s taxonomy, corresponding to dimensions 2, 4, and 6 out of the total $D=23$. Its multi-hot encoding vector is therefore

|     |                |     |
|-----|----------------|-----|
|     | $$\mathbf{v}^{(i)}=(0,1,0,1,0,1,0,\ldots,0)\in\{0,1\}^{23},$$ |     |

where the nonzero entries indicate the relevant capability dimensions and all remaining positions are zero. If the model assigns this instance a scalar prediction score $s^{(i)}=0.8$, the projected dimensional score vector becomes

|     |                |     |
|-----|----------------|-----|
|     | $$\mathbf{s}^{(i)}=0.8\cdot\mathbf{v}^{(i)}=(0,0.8,0,0.8,0,0.8,0,\ldots,0).$$ |     |

Thus, the same prediction score is assigned to each of the associated capability dimensions (2, 4, and 6), while having no effect on the others. Aggregating such vectors across all evaluation instances yields cumulative performance scores for each capability dimension.

## Appendix N Model-wise Sensitivity to Messy Queries

We examine whether sensitivity to messy user queries is shared across the evaluated model configurations. Under the Unrestricted setting, we compare each configuration’s Total Score on Messy Query inputs with its own performance on the corresponding Clean Query inputs.

Fig [8](https://arxiv.org/html/2610.02206v1#A14.F8) shows that every tested configuration experiences a decrease in Total Score. Most configurations lose approximately 3 percentage points, while the two most sensitive configurations lose more than 4 percentage points. Even the smallest observed decrease is 1.98 percentage points. This consistent trend across the tested configurations suggests that degradation to messy queries is not confined to a single model family, and how to deal with messy user queries remain a systematic challenge for natural-language-to-CLI translation task.

## Appendix O Limitations

KaliBench is designed as a deterministic and reproducible benchmark for evaluating NL–to–CLI function calling, and it inherits several limitations intrinsic to the CLI ecosystem and its documentation sources. Ground-truth commands are derived from Kali Linux tool manuals available at dataset construction time. As these manuals evolve across versions through the addition, deprecation, renaming, or reinterpretation of flags, some canonicalized commands may become outdated as upstream documentation changes. In practice, such effects are limited, as tools often maintain backward compatibility, and evaluation in the hinted setting is further insulated from drift by explicitly providing models with the tool documentation to follow.

In addition, real-world tool documentation may occasionally contain inconsistencies or errors. For example, the regtree manual lists the -V option with conflicting semantics (`-`V, `--`no-values and `-`V, `--`version), and several tools in the Impacket family document atypical short-option forms (e.g., -aesKey) that differ from common usage conventions (e.g., `--`aesKey). Such cases reflect the diversity and historical evolution of CLI interfaces rather than issues specific to KaliBench, and they make fully deterministic canonicalization inherently approximate when documentation diverges from observed behavior or when multiple variants coexist.

Our LLM-as-Verifier pipeline substantially filters hallucinated flags and arguments by grounding validation in official manuals, but it remains imperfect; human verification of a random subset indicates that residual errors are limited. Similarly, the alias-aware scoring mechanism relies on semi-automatically extracted alias groups and cannot capture all historical, distribution-specific, or community-adopted variants.

Taken together, these considerations position KaliBench as a controlled and well-defined abstraction of real-world CLI tool invocation. It is designed to support systematic, fine-grained evaluation of NL-to-CLI translation, while complementing execution-based or agentic evaluations in operational cybersecurity environments.
